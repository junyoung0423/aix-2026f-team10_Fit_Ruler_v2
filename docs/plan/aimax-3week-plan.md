## 역할 분담

PR은 한 사람이 한 주에 2개씩 올린다. 리뷰어는 PR마다 그 결과물을 받아 쓰는 사람으로 정하고, 1명으로 제한하지 않는다. C의 일이 가장 많아 #5 견본 검색(순수 계산 로직)은 B로 옮겼고, A가 #3 티셔츠 후보 선별을 돕는다.

| 역할 | 맡는 이슈 | 주로 만지는 폴더 |
|---|---|---|
| A 화면과 사용성 | #9 입력·결과 화면, #12 상태 표시, 관리 화면, 사용성 테스트, #13 설치 안내 검수·`PROMPTS.md` 정리, #3 후보 선별 지원 | `web/`, `docs/ux/` |
| B 서버와 핏 판정 | #1 공통 스키마·포트·가짜 어댑터(주도), #2 핏 계산, #5 견본 검색, 작업 실행기·API, #12 실패 처리, #13 통합 실행 | `fitting/domain/`, `ports/`, `fit/`, `services/`, `server/`, `.github/` |
| C 의류와 착장 렌더 | #3 데이터 등록, #4 견본집 생성, #6 견본 최적화, #8 Blender 착장(옷·원단), #10 정면 렌더 클립, #11 의류 형태 검증 협업 | `fitting/catalog/`, `adapters/aihub·garmentcode·blender/`, `tools/` |
| D 몸과 실사화 검증 | #7 SMPL 몸 생성·측정, #8 착장 점검(몸·충돌), #10 fal/LTX 실사화, #11 대표 프레임·색·실루엣 검증 | `fitting/body/`, `verify/`, `adapters/smpl·fal_ltx·media·meshcheck/` |

#1과 #13은 활동지대로 전원이 확인한다. 폴더를 사람별로 나눠 두면 PR끼리 충돌이 거의 없다. 아래 구조는 Python(FastAPI)·React 기준 예시이고, 이미 정한 기술이 있으면 폴더 이름만 맞추면 된다.

## PR·리뷰 규칙

main에는 PR로만 들어가고, 머지 조건은 주차별 표에 적힌 리뷰어 전원의 승인 + CI 통과다. 리뷰는 요청 후 24시간(평일) 안에 한다.

1. **브랜치**: `종류/이슈번호-요약` — 예: `feat/2-fit-calculator`. 종류는 `feat`·`fix`·`docs`·`spike`·`chore`.
2. **커밋**: 활동지 규칙대로 이슈 번호로 시작한다 — `#2 가슴 여유량 계산 추가`.
3. **PR 제목·본문**: `[#2] 핏 판정 계산기`. 이슈를 끝내는 PR에만 `Closes #2`, 중간 PR은 `Refs #2`를 쓴다. GitHub은 `Closes`가 붙은 이슈를 머지 때 자동으로 닫는다.
4. **개수와 크기**: 한 사람이 한 주에 PR 2개(주 중반 1개, 점검일 전 1개), 3주 동안 모두 24개다. PR이 커지므로 작업을 시작하면 바로 Draft PR로 올려 중간에 의견을 받고, 커밋은 작게 나눈다.
5. **리뷰**: 리뷰어는 PR마다 그 결과물을 받아 쓰거나 영향을 받는 사람으로 정하고, 1명으로 제한하지 않는다(주차별 표의 ‘리뷰어’ 칸). 지정된 리뷰어는 요청 후 24시간 안에 보고, 작성자도 리뷰 의견에 24시간 안에 답한다. 리뷰어가 이틀 넘게 자리를 비우면 작성자가 다른 팀원으로 바꾼다.
6. **머지**: 지정된 리뷰어 전원 승인 + CI 통과 후 작성자가 Squash merge하고 브랜치를 지운다. 충돌은 작성자가 main을 받아 해결한다.
7. **계약 변경**: `fitting/domain/`·`fitting/ports/`를 바꾸는 PR은 단톡방에 먼저 알리고, B와 그 계약을 쓰는 사람이 모두 리뷰한다(B가 작성자면 쓰는 사람만). 필드 삭제·이름 변경 대신 기본값 있는 필드를 추가한다.
8. **CI(GitHub Actions)**: ruff + pytest(가짜 어댑터만) + 웹 lint·타입 검사·빌드. Blender·SMPL·fal이 필요한 테스트는 `blender`·`smpl`·`fal` 마커로 CI에서 빼고, 작성자가 로컬 실행 결과를 PR에 붙인다. fal은 비용이 들어 CI와 테스트에서 호출하지 않는다. 계층 규칙은 import-linter로 자동 검사할 수 있다(선택).
9. **커밋 금지**: `.env`(`FAL_KEY`), `models/`(SMPL 모델은 재배포 불가), AI Hub 원본, `artifacts/`(.blend·영상·메시). 큰 결과물은 팀 공유 드라이브에 두고 위치를 README에 적는다.
10. **저장소 설정**: main 브랜치 보호 규칙으로 PR 필수·승인 1명 이상·CI 통과를 강제하고, 지정 리뷰어 전원 승인은 팀 규칙으로 지킨다. 비공개 저장소에서는 소유 계정이 GitHub Pro(조직 소유면 Team)여야 이 규칙이 적용된다(학생은 Student Developer Pack으로 Pro 무료). 킥오프 날 B의 초기 커밋(폴더 구조·CI·PR 템플릿)만 보호 규칙을 켜기 전에 main에 바로 올린다.
11. **AI 사용 기록**: AI를 쓴 PR은 무엇을 어떻게 썼는지 `PROMPTS.md`에 같은 PR에서 추가한다. 마지막 정리는 A가 A6에서 한다.

PR 템플릿 — `.github/pull_request_template.md`에 그대로 넣는다.

```markdown
## 관련 이슈
Refs #   (이슈를 끝내는 PR이면 Closes #)

## 바꾼 것
- 

## 확인 방법
- [ ] pytest 통과 (마커 테스트를 돌렸다면 결과 첨부: blender / smpl / fal)
- [ ] 화면 변경이면 스크린샷 첨부
- [ ] AI를 썼다면 PROMPTS.md에 기록

## 리뷰어 체크
- [ ] 완료 조건 또는 PR 범위를 충족하고, 새 로직에 테스트가 있다
- [ ] 로직 코드가 외부 SDK(bpy·smplx·fal_client)나 adapters/를 직접 import하지 않는다
- [ ] 단위(cm)·단면/둘레 구분·스키마 필드 이름이 domain/과 같다
- [ ] 비밀키·대용량 파일·SMPL 모델·AI Hub 원본이 없다
```
